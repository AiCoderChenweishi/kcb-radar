# 科创板每日情报雷达 · 项目档案

> 本文档是项目的**信息记录载体**。每日简报本体是 Web 看板（见文末"访问方式"），本文档记录架构、口径、决策依据与运行状态。

## 一、项目目标

面向战略岗决策需求，每日自动采集**科创板全部上市公司**（当前 619 家）的公开信息，产出可直接支撑决策的情报：

| 需求 | 落地数据源 | 落点 |
|---|---|---|
| 业务要闻 | 东方财富个股资讯检索（619 家全覆盖） | 看板「要闻」 |
| 财务信息摘要 | 东方财富 F10 利润表 + 主要指标（营收/净利/同比/ROE/毛利率/总资产/EPS） | 看板「财务」「全量数据」 |
| 公司估值信息 | 行情快照 PE/PB/市值 + **自算 PE/PB 近 3 年历史分位** | 看板「估值」 |
| 热点新闻 | 东方财富 7×24 快讯（iFinD 额度可用时用同花顺热度） | 看板「今日全景 › 热点事件流」 |
| 券商报告与观点 | 东方财富研报中心（全市场一次，券商/评级/评级变化/三年 EPS 预测） | 看板「券商观点」 |
| 法定披露公告 | 东方财富公告（全市场分页，含公告类型分类） | 看板「公告」 |

## 二、已确认的决策

| 决策项 | 结论 |
|---|---|
| 覆盖策略 | **分层**：全量 619 家基础层（每家每日必采）＋ 自动高信号层 |
| 重点关注池 | **不设人工名单**（全市场平权）。高信号由脚本按可验证事实自动打分 |
| 交付形态 | **Web 应用**（本地 Node 服务 + 静态看板） |
| 执行时间 | **每日 07:30**（覆盖前一交易日收盘后至清晨的全部消息） |

> "分层"与"不设关注池"并不矛盾：分层不靠人工偏好，而靠数据本身说话——
> 券商评级/目标价变化、重大公告、业绩预告、PE 历史分位极值、当日大幅波动、增速突变
> 都会自动把相关公司顶到首页。这样既不会对全市场厚此薄彼，也不会让重点淹没在 619 家里。

## 三、系统架构

> **注意：2026-10-21 架构已因 iFinD 额度限制做过一次根本调整**，详见 4.13–4.15。
> 当前版本以东方财富为主力源，iFinD 只承担不可替代的少数指标。

```
① 采集层（Node 脚本，零依赖）
   名单  → iFinD search_securities（619 家；额度不足时回落本地缓存 CSV）
   行情  → 东方财富 push2 clist fs=m:1+t:23（7 次分页）
           全量 622 家的当日涨跌幅 / PE / PB / 市值 / 行业分类
   研报  → 东方财富研报中心 report/list（code=*，1~2 次）
           全市场研报，含券商、评级、评级变化、三年 EPS 预测与对应 PE
   公告  → 东方财富公告 np-anotice-stock（按日期窗口分页，~40 次）
           全市场公告，筛出科创板，含标题、日期、公告类型
   要闻  → 东方财富个股资讯检索（每家 1 次，619 次）
   财务  → iFinD get_stock_summary（5 家/次，124 次）
           额度耗尽时自动降级为东方财富 F10 RPT_F10_FINANCE_GINCOME（619 次）
   分位  → iFinD get_security_indicators（124 次）★ 唯一不可替代
   热点  → iFinD search_trending_news（15 次）
   ------------------------------------------------------------
   全量一轮：36 秒（东方财富主力）/ 34 分钟（纯 iFinD 路径）
        ↓
② 归一层（parser.js）
   Markdown 表解析、研报抽取、串台过滤、导航噪声过滤、板块快讯过滤
        ↓
③ 研判层（insight.js）
   信号打分 + 简报组装 + 跨日观点变化对比
        ↓
④ 存储层（store.js）→ ⑤ 服务层（server.js）→ ⑥ 前端看板（public/）
```

**为什么必须脚本化**：619 家 × (要闻+财务+估值+研报+公告) 的原始数据量在百万 token 级，
任何单次 LLM 上下文都扛不住。脚本把原始数据在磁盘上消解掉，模型只读归一后的结构化字段做研判。

## 四、关键实现决策与踩坑记录

### 4.1 mcode-tools 必须直连 Electron 入口

`.cmd` shim 在 Windows 下会吃掉 JSON 参数的引号（报 `Connector arguments must be valid JSON`），
而 Node 的 `spawnSync` 不带 shell 时无法执行 `.cmd`（ENOENT）。
真实入口是 Electron 以 Node 模式运行 `cli.mjs`：

```
"MiniMax Code.exe" "resources/resources/mcode-tools/cli.mjs" connector call <tool> --args-file <file>
```

`src/connector.js` 在运行时解析 `~/.minimax/bin/mcode-tools-cn.cmd` 反推 exe/cli 路径与环境变量，
不硬编码路径。**认证 broker 的命名管道端点必须逐字透传**——反斜杠一旦被二次转义，
cli 会判定为非 canonical lease 路径并直接拒绝连接。

### 4.2 参数一律走 `--args-file`

`--args` 内联 JSON 会被批处理 shim 改写。所有调用统一写临时文件再传路径。

### 4.3 iFinD 表头与数据列顺序不一致 ⚠️

表头写「证券代码｜证券简称｜市盈率…」，**实际数据行是「容百科技｜688005.SH｜…」——代码与名称反了**。
硬按表头下标取会把公司名当代码，整张表挂到错误的 key 上，表现为"财务覆盖 0/619"。
解析器改为以数据行实际形态校正列位（`identifyCols`）。

### 4.4 Markdown 表格分隔行不能作为表结束标志

`|---|---|` 只是列宽定义，跳过即可。若在此处 `push` 表格，**首行数据会被当成表头**，
第二行起的数据行全部丢失。

### 4.5 语义检索会串台 ⚠️

查亚虹医药的研报时，iFinD 返回过英诺特的业绩预测片段。
归一层强制做归属校验：条目必须提及目标公司，且若同时出现另一家科创板公司名/代码则判为串台丢弃。
**检测必须用全市场 619 家名单**——用抽样名单做检测等于没有检测。

### 4.6 目标价不能有宽松兜底

早期版本用 `/(\d+)\s*元/` 兜底，结果把「预测2026年每股收益 0.92 元」当成目标价。
每股收益和目标价长得一样但含义完全不同，这类误差会直接带进简报。
现要求数字必须紧邻「目标价」字样，并支持区间取中值。

### 4.7 一致预期 ≠ 个别券商报告

iFinD 的「盈利预测-业绩预测详表-研报评级」是**卖方一致预期汇总**，
和「西南证券-亚虹医药-…-261008」这类**个别券商报告**是两回事。
两者混在一起会让人误以为每条都是独立券商观点，故分类为 `consensus` / `broker_report`，
看板分别标注。

### 4.8 指数数据拿不到，用市场宽度替代

`get_security_indicators` 查「科创50指数」会把 000688 解析成深市国城矿业；
恒生接口只覆盖沪深个股不含指数；快查 `iwencai_astock_special` 调用报错。
**替代方案**：用智能选股接口的 `selectedSecuritiesCount` 直接数家数（上涨/下跌/涨超5%/跌超5%/涨停/跌停/市值分布），
指数点位则从新华财经收盘播报正文里抽取。

### 4.9 枚举参数不能自造

- `search_trending_news` 的 `time_scope` 只接受 `6小时 / 24小时 / 近一周`（传「7天」报 -32602）
- `industry_name` 只接受 30 个固定行业名（传「半导体」「生物医药」报 -32602）
- `industry_name` 为全市场检索时**不能传空串**，要直接不带这个键

### 4.10 快查的舆情工具不能用于按公司采集

`news_search_public_opinion_news` 的 `sec_code` / `search_title` 过滤参数在当前封装下不生效，
实测仍返回全库 693 万条。快查保留其**工商/股东/风险/筛选**能力作为补充，不承担要闻采集。

### 4.11 `spawnSync` 的 timeout 杀不掉 Electron 子进程 ⚠️

mcode-tools 是 Electron 以 Node 模式运行的。`spawnSync(..., { timeout })` 只能终止直接子进程，
而 stdout 管道被孙进程持有，**超时后 spawnSync 依然不返回**。
实测一次全量采集里，`search_news` 和 `get_security_indicators` 两个调用永久挂住，
整轮采集停在那里 40 分钟没有任何输出。

现在改成异步 `spawn` + 超时后 `taskkill /PID <pid> /T /F` 杀整棵进程树，
并额外加一道**阶段级看门狗**（`PHASE_DEADLINE_MS`，默认 25 分钟）：
任何单个阶段超时就被放弃，已采到的数据照常保留并落盘。

**⟹ 判据：凡是长跑型批量采集，必须有"单调用超时 + 进程树强杀 + 阶段看门狗"三件套，
否则一次接口挂死就会让整条流水线静默停住。**

### 4.12 行情层用东方财富而不是 iFinD

iFinD 的指标接口拿全量 622 家的当日涨跌幅和行业分类，要 5 只/次 → 124 次调用，
而且**没有行业分类**。东方财富 `push2.eastmoney.com/api/qt/clist/get` 用
`fs=m:1+t:23`（科创板板块口径）一次 100 条，7 次分页即可拿到全量
涨跌幅/PE/PB/总市值/流通市值/行业分类，快一个数量级。

### 4.13 iFinD 连接器会随机瞬时失败 —— 不是并发问题 ⚠️

现象：`connector_tool_error: Connector tool execution failed (latency_ms=0)`。
`latency_ms=0` 说明是**瞬时拒绝**，不是超时。

误判过程：一开始以为是并发太高（16 路 → 失败 608/1500，财务只覆盖 30/619），
于是把并发降到 6 并加长调用间隔——结果更慢，覆盖率并没有变好。
做基准测试才发现真相：

| 并发 | 成功率（24 次调用，重试 1 次） | 耗时 |
|---|---|---|
| 4 | 75% | 88s |
| 6 | 88% | 107s |
| 8 | **96%** | 72s |
| 12 | 83% | 98s |

**失败率与并发不成正比**。串行单次调用也有约 33% 概率失败 —— 是随机抖动，
拉长间隔完全无效，只会让整体变慢。

**⟹ 正确解法不是调并发，而是「多次重试 + 失败修复轮」**：
1. 每次调用重试 3 次（4 次尝试），单次成功率 70% → 累计成功率约 99.2%
2. 主批次跑完后，对仍失败的项**降并发单独补采**（`runWithRepair`）
3. 间隔只做温和兜底（封顶 500ms），不指望它解决可靠性

**⟹ 通用判据：看到 `latency_ms=0` 或"瞬时失败"，先做基准测试建立"并发-成功率"曲线，
再决定是调并发还是加重试。别凭直觉猜。**

### 4.14 真正的根因：iFinD MCP 请求额度耗尽 ⚠️⚠️

上面那 608 条失败**不是并发问题，是额度问题**。踩坑路径值得完整记录：

1. 并发 16 → 失败 608/1500，财务只覆盖 30/619
2. 误判为并发太高 → 降到 6 路、拉长调用间隔 → 更慢，覆盖率没变好
3. 做并发基准（4/6/8/12）→ 成功率 75%/88%/96%/83%，**与并发不成正比**
4. 串行单次调用也 33% 失败 → 说明是随机抖动
5. **改用"重试 + 修复轮"后覆盖率上来了，但失败总量仍在上升**
6. 最终在一次单点调用里看到返回体的正文：
   > 当前账户MCP请求用量已耗尽，可以访问 ifind-mcp 官网，在产品订阅界面选购/升级权益…

**⟹ 最危险的特性：这个错误是 HTTP 200 + 正常的业务结构（`{answer: "..."}`），
不是异常、不是空数组。**如果不做特征串识别，采集器会把它当成"这家查无数据"，
整轮跑完产出一份**看起来完全正常、实际大面积为空**的数据集。

**⟹ 判据：任何返回"看起来成功但内容是解释性文字"的接口，都必须做正文特征校验，
把额度/权限/限流类提示识别成硬错误并立刻熔断。**

**⟹ 更根本的教训：调用量必须先算清楚再设计。**
每天 619 家 × (要闻+公告+研报) = 1500 次调用，直接打爆了免费额度。
**默认额度撑不起"全量×逐家×多接口"的朴素设计，必须引入免费源做主力。**

### 4.15 架构调整：主力源换成东方财富

额度用完后换源，发现东方财富的免费接口几乎能覆盖全部需求：

| 需求 | 东方财富接口 | 调用量 | 关键收获 |
|---|---|---|---|
| 行情/估值/行业 | `push2.eastmoney.com/api/qt/clist/get?fs=m:1+t:23` | 7 | 全量 622 家，带行业分类 |
| 券商研报 | `reportapi.eastmoney.com/report/list?code=*` | 1–2 | **一次拿全市场研报**：券商、评级、评级变化（lastEmRatingName）、三年 EPS 预测与对应 PE、分析师、研报 ID |
| 公告 | `np-anotice-stock.eastmoney.com/api/security/ann` | –40 | 支持 begin_time/end_time 服务端过滤；含公告类型分类 |
| 个股要闻 | `search-api-web.eastmoney.com/search/jsonp` | 619 | 带日期、标题、摘要、链接 |
| 财务摘要 | `datacenter.eastmoney.com/securities/api/data/v1/get?reportName=RPT_F10_FINANCE_GINCOME` | 619 | 营收/净利/同比/毛利率/ROE，兜底用 |

**⟹ 结果：全量一轮从 34 分钟降到 36 秒，iFinD 日调用量从 1500 降到 124。**

**⟹ 研报口径的差异（重要）**：
- 东方财富给的是**真实券商研报**：一周内科创板约 16 篇，覆盖 15 家公司（卖方覆盖高度集中在大市值标的）
- iFinD 给的是每家公司的"研报评级/一致预期"聚合页：839 条，覆盖面更广，但含无实质内容页
- 两者不能混为一谈，界面里分别标注「券商报告」与「一致预期」

### 4.16 东方财富按公司检索会带出板块快讯

查"睿创微纳"会返回"20cm速递 | 科创100ETF国泰标的指数涨超2%，资金持续净流入"——
因为公司在 ETF 成分里。这类内容讲的是板块不是公司，会污染公司画像。
已加 `isMarketLevelNoise()` 过滤（ETF/指数涨超/板块/资金流/龙虎榜/融资融券/速递系列等），
实测单轮剔除 946 条。

**⟹ 判据：按实体检索新闻时，必须区分"实体相关"与"实体所属集合的相关"。
判定方式看标题讲的是谁 —— 讲板块/指数/资金的一律不属于公司层。**

### 4.17 单一数据源会整体失联 —— 必须做多源兜底 ⚠️

东财 push2 用多了会被 IP 级封禁（socket hang up），
且**同源的 push2his 也会被连带阻断**，datacenter 系却照常工作。
这暴露了"把某类数据押在单一 host 上"的风险。

现在每个环节都有主源 + 备源 + 缓存：

| 环节 | 主源 | 备源 | 兜底 |
|---|---|---|---|
| 个股行情 | 东财 push2（带行业） | **腾讯 qt.gtimg.cn**（批量 60 只/请求，11 次拿全 619 家） | 本地快照缓存 |
| 指数 | 东财 push2 | 腾讯 sh000688 / sh000680 / sh000698 | 沿用上次 |
| 行业/省份/主营/员工数 | 东财 F10 公司概况 | **东财 F10 业绩报表的 BOARD_NAME** | 档案缓存（慢变属性，永久复用） |
| 财务摘要 | iFinD get_stock_summary | 东财 F10（两张报表拼，见 4.19） | — |
| **PE / PB 历史分位** | **东财历史估值序列自算（见 4.21）** | iFinD（口径不可信，仅留作参考字段） | — |
| **事件类型分布** | **自算：公告/要闻正文 + 事件词典（见 4.23）** | — | — |
| **卖方关注行业** | **自算：研报 × 行业分类聚合** | — | — |
| 个股要闻 | 东财资讯检索 | — | 12 小时 TTL 缓存 |
| 公告 | 东财公告（全市场分页） | — | — |
| 券商研报 | 东财研报中心（近期 + 90 天两段窗口） | — | — |

**⟹ 缓存的三条原则**：
1. **行情快照**（每日变）：成功即落盘，失败读缓存并标记 stale —— 宁可标"缓存"也不能写空数据
2. **公司档案**（慢变）：只在缺失时拉，收敛后每日 0 次调用
3. **个股要闻**（小时级变）：12 小时 TTL，避免同一天反复跑把接口打限流

**⟹ 判据：任何"每日必跑"的外部数据源，都要问一句"它挂了这轮怎么办"。
只有一种回答（没有备源也没有缓存）的环节，本质上是把系统的可用性押在别人的服务器心情上。**

### 4.18 客户端 fetch 不结算响应体，XHR 却正常 ⚠️

现象：看板页面一直停在"加载中"。排查链条：
- 服务端 `/api/brief` 响应 **200、毫秒级写完**（access.log 里能确认）
- 响应体 87KB、963KB、2MB、gzip 290KB **全部复现**
- `/api/dates`（几十字节）却能正常返回
- 换成 1MB 的 `/api/ping` 也能正常返回
- 去掉 gzip、加 `Connection: close`、关掉 keep-alive —— 全部无效

最后改用 **XMLHttpRequest** 一次就通了。

**⟹ 判据：浏览器端"接口调不动"时，先把 fetch 换成 XHR 试一次。
fetch 的响应体结算在某些嵌入式渲染器里不可靠，XHR 老老实实。**

顺带的设计改进（也解决了大载荷卡顿）：
- `/api/brief` 只给汇总与表格（首屏 –300KB）
- `/api/feeds?type=news&page=1&size=100` 信息流按 tab 分页按需拉
- `/api/company?code=xxx` 单家公司详情，点开抽屉时再拉

### 4.19 东财 F10 财务要用两张报表拼

单张表都缺字段：
- `RPT_LICO_FN_CPD`（业绩报表）：营收、归母净利、营收/净利同比、EPS、**BOARD_NAME（行业分类）**
- `RPT_F10_FINANCE_MAINFINADATA`（主要指标）：**加权ROE、销售毛利率、总资产、每股净资产**
- `RPT_F10_FINANCE_GINCOME`（利润表）没有 ROE / 毛利率 / 净利率 —— 别用它

**⟹ 坑：两张表默认排序不同，必须显式 `sortColumns=REPORT_DATE&sortTypes=-1`，
否则取到的是一年前的旧数据（澜起科技返回 2025-06-30 而非 2026-06-30）。**

净利率东财没直接给，用 `归母净利 / 营业总收入` 算。

### 4.20 iFinD 的「PE(TTM)分位数」不可信，改为自算 ⚠️

iFinD 指标接口的「市盈率(PE,TTM)分位数」实测返回**三家不同股票都恰好 100.0**
（澜起科技 / 华兴源创 / 中微公司）。而自算结果是 37.5 / 93.2 / 18.4。

以澜起为例：当前 PE_TTM 70.81，其 7 年 PE_TTM 中位数 80.4、最大值 151.0，
**不可能处在历史最高位**。该指标至少在本次取数环境下不可信。

更要命的是它被用作高信号公司的加分项（"PE 分位 100%（历史极高）"），
结果**一半以上的高信号公司挂着"估值极高"的假标签**，高信号排序被严重扭曲。

**⟹ 改用东财 `RPT_VALUEANALYSIS_DET`（每股约 1757 个交易日的 PE_TTM / PB_MRQ 序列）自算分位**：
- 主口径：近 3 年（750 个交易日）
- 参考口径：全历史（1757 天）
- 负 PE（亏损公司）不参与分布计算，与主流口径一致
- 额外产出 **PB 历史分位**（iFinD 没有）

改后校验：394 家有分位、中位 46.9、**恰好 100 的 0 家**、≥95% 共 29 家、≤5% 共 74 家。
抽查：澜起 36.7%（低于自身中位）、中微 27.9%、海光 13.9%、英诺特 96.1% —— 全部站得住。

**⟹ 通用判据：任何"分位数/排名/分档"类指标，先拿可独立验证的原始序列手算一遍再采信。
分布出现大量恰好 100 / 0 的整齐值，基本是指标口径或解析出了问题，不是市场现象。**

### 4.22 研报要用两段窗口，否则严重低估卖方覆盖 ⚠️

东财研报中心的返回是**研报增量流**，不是全量清单：

| 窗口 | 全市场 hits | 科创板 | 覆盖公司 |
|---|---|---|---|
| 7 天 | 102 | 16 篇 | **15 家** |
| 30 天 | 344 | 16 篇 | 15 家 |
| **90 天** | 3213 | **438 篇** | **234 家** |

而且单只查询 `code=688008` 在 30 天窗口返回 **0**，90 天窗口才有 4 篇
（澜起最近一篇是 09-02）——**只看短窗口会得出"科创板基本没有卖方覆盖"的错误结论**。

另外 `pageSize` 上限 100，必须翻页（90 天 = 32–33 页，约 8.7 秒，全免费）。

现在采集器跑两段：
- 7 天 → 每日新增研报（进要闻流）
- 90 天 → **卖方覆盖全景**（谁被覆盖、最新评级/目标价/三年 EPS 预测/目标价空间）

实测：科创板 423 篇 / 228 家公司 / 27 家券商，评级 买入283 增持117 持有1。
看板新增「卖方覆盖」页签，可按 买入增持 / 有目标价 / 评级上调 过滤。

**⟹ 判据：查"谁被覆盖""历史观点"这类存量问题时，短窗口查询会静默给你一个偏小的答案。
先用长窗口验证数量级是否合理，再决定窗口长度。**

### 4.23 中文没有空格，主题聚类不能用 n-gram ⚠️

第一版想从 5,572 条要闻/公告标题里做主题聚类（"被多少家科创板公司同时报道 = 科创板热点"），
用 2–8 字 n-gram 切词，结果切出来全是碎片：

```
1. 的公   覆盖310家      5. 年第   覆盖241家
2. 股东   覆盖305家      9. 东会   覆盖215家
4. 议公   覆盖251家     12. 次临   覆盖211家
```

"议公""年第""东会"没有任何意义。中文不做词切分，字面 n-gram 必然是垃圾。

**⟹ 换成事件类型词典 + 正则**，23 类科创板常见事件，22ms 算完：

| 事件 | 覆盖公司 | 事件 | 覆盖公司 |
|---|---|---|---|
| 投资者调研 | 201 | 业绩预增 | 76 |
| 业绩说明会 | 186 | 研发里程碑 | 75 |
| 再融资 | 112 | 股权激励 | 74 |
| 董监高变动 | 111 | 重大合同中标 | 71 |
| 股份回购 | 110 | 大宗交易 | 68 |
| 股东减持 | 108 | 业绩预亏 | 58 |
| 重大资产重组 | 36 | 风险警示 | 29 |
| 对外投资 | 30 | 监管问询处罚 | 19 |

每类都带涉及公司清单和可点击的原文示例链接。

**⟹ 判据：中文文本的关键词提取，必须用词典+正则或分词器，不能用字面 n-gram。
需要"事件/主题"这类语义分类时，穷举业务词典比机器切词更准、更可解释。**

### 4.21a 送给 Bot 的数据必须先做摘要层

让 Bot 直接读 `data\daily\<日期>.json`（5.3MB）会卡住——实跑一次主编任务跑了 17 分钟没出来。
加了 `scripts\digest.cjs`：预先算好 494KB 的摘要（25 家高信号 / 60 家卖方覆盖 /
178 家公司轻量档案 / 23 类事件 / 46 个卖方行业），采集脚本每次自动生成。
完整明细仍留在原 JSON 里，需要时按摘要里的 `paths.full_dataset` 查。

**⟹ 判据：人写的 Bot 提示词要带文件大小意识。给模型 5MB 的输入不是"给上下文"，
是给一个必然超时的任务。**

### 4.21b 基线版与判断版简报必须用不同文件名

原来两者都写 `out\brief-<日期>.md`，任何时候跑一次基线脚本就会把 Bot 写的
判断层简报覆盖掉。已改为基线版写 `brief-baseline-<日期>.md`，判断版仍是
`brief-<日期>.md`；`publish_brief.cjs` 优先发判断版，没有才回落基线版。

### 4.21c 读文件取 H1 标题前必须剥 BOM

PowerShell 的 `Set-Content -Encoding UTF8` 会写 BOM，导致 `/^#/` 匹配失败，
`titleOf()` 静默回落到默认标题 → **找错节点、覆盖到别的日期的文档上**。
现已先 `replace(/^\uFEFF/,'')`，并在 H1 日期与文件名日期不一致时按文件名归档并告警。

### 4.21d 研报条目要按 (公司,日期,标题,券商) 去重

同一家公司同一天可能有多篇研报，按 (公司, 日期) 展开会让同一篇在列表里出现两次
（实测 22 条里 4 条是重复）。去重后 18 条。

**⟹ 通用判据：把多来源数据合并进同一张列表时，先定好唯一键再去重，
否则"条数"会骗人——看板和简报里的"研报 N 篇"可能含重复。**

### 4.21 东财历史估值序列可自算分位（补上 PE 分位缺口）

`RPT_VALUEANALYSIS_DET` 每只股票约 1757 个交易日（7年）的
PE_TTM / PB_MRQ / 收盘价 / 涨跌幅 / 总市值，单次请求取回（≈170ms/只）。
619 家并发跑 **20 秒**完成，**完全免费、不依赖 iFinD 额度**。

这直接补上了 iFinD 额度耗尽后唯一缺失的"估值分位"能力，同时修正了 4.20 的错误口径。

**⟹ 判据：外部数据源缺失一个能力时，先去找"有原始序列可自算"的免费源，
而不是只能等额度恢复或加购。自算口径还更可控。**

## 七、自动化链路

| 环节 | 机制 | 时间 | 说明 |
|---|---|---|---|
| 全量采集 | Windows 计划任务 `MavisKcbRadarCollect` | 每日 07:30 | 确定性工作，不走 LLM 回合；约 40–70 秒 |
| 数据层巡检 | MiniMax Bot「科创数据官」 | 每日 08:30 | 覆盖完整性、失败清单、跨日突变 |
| 产业舆情研判 | MiniMax Bot「产业舆情官」 | 每日 08:50 | 高信号公司的产业归类、研报假设、催化剂 |

**分工原则**：采集是确定性工作，交给计划任务；模型只做"把数据变成判断"。
采集若走 LLM 回合，会受回合超时与稳定性影响；一旦某次挂住，链路就断了。

Bot 之间用**文件交接**（`out/data-report-<日期>.md`、`out/intel-report-<日期>.md`），
不靠聊天上下文传递——文件交接不会因为某一步失败就整条断掉。

**并发保护**：`data/collecting.lock` 锁文件 + 服务端校验，
防止"手动刷新"和"计划任务"同时跑出两个采集进程抢同一个输出文件。

### 工程纪律：工作区 ↔ 部署目录

会话工作区 `<sessions>\<id>\workspace` **本身**就是工程源（不再有 `web/` 子层），而 `scripts/deploy.cjs` 的方向是 **工作区 → 稳定位置**。因此：

## 十三、2026-10-21 20:40 定位到的环境级单点故障：本地代理

这是本轮最隐蔽、影响最大的一个发现，值得单独记。

### 现象

同一时间段内，三件事同时出现：

| 现象 | 报错 |
|---|---|
| 飞书 API 全挂 | `proxyconnect tcp: dial tcp 127.0.0.1:7892: connectex: No connection could be made because the target machine actively refused it` |
| connector 平台全挂 | `Network request failed for /minimax-cloud/api/v1/connectors/connected-tools/list: fetch failed` |
| 采集从 62 秒暴涨到 836 秒 | 15 个调用各自跑满重试 + 退避 |

初看像是"飞书挂了 + connector 平台挂了 + 外部源变慢"三件独立的事，实际上是**同一件事**。

### 根因

机器上设了全局环境变量：

```
HTTP_PROXY  = http://127.0.0.1:7892
HTTPS_PROXY = http://127.0.0.1:7892
```

但那个本地代理客户端（7892 端口）**当时没有在运行**。`Test-NetConnection 127.0.0.1 - 7892` → `TcpTestSucceeded = False`。

关键验证：**绕过代理直连，一切正常**——
- `open.feishu.cn` 直连可达（返回业务 404，说明请求到了服务器）
- `data.eastmoney.com/report/info/<code>.html` 直连 HTTP 200、35,557 字节
- Node 的 `https.get` 本来就不自动读代理变量，所以东财抓取一直是直连 —— 这也是为什么只有走 lark-cli / mcode-tools 的链路会挂

**也就是说：整条自动化链路唯一的单点故障，就是这台机器上的一个本地代理进程。** 代理没开 → 飞书发不出、connector 调不动、采集还会被重试拖成十几分钟。

### 修复（两侧都加）

1. `scripts/lark.cjs`：从错误特征识别代理故障（`proxyconnect` / `127.0.0.1:7892` / `socks proxy`），命中后**摘掉 `HTTP_PROXY/HTTPS_PROXY/ALL_PROXY` 及其小写变体、置 `NO_PROXY=*`，直连重试一次**，并记住"代理已坏"，后续所有调用直接走直连。
2. `src/connector.js`：同一套判据。识别到代理故障后，本轮后续子进程环境都走直连；并在 `callTool` 里做了一次"同 attempt 直连重试"（不消耗重试预算）。

### 实测

- 飞书：首次调用报代理错误 → 自动切直连 → 成功（`wiki +node-list` 返回 15 个节点）。
- connector：自动切直连后成功连上 iFinD，随即返回 `QUOTA_EXHAUSTED` —— 这也把之前"平台不可达"的假象澄清了：**平台是好的，是代理挡住了；iFinD 额度确实耗尽。**

### 给运维的三条

1. **不要在依赖常驻进程的机器上把"代理必须开着"当成隐含前提。** 现在两侧代码都能在代理挂掉时自愈直连。
2. 代理恢复后无需重启任何进程（下次调用会自动走回代理；已标记为 broken 的进程内状态需重启脚本才恢复）。
3. **排查"某个外部服务突然全挂"时，先查本机代理端口**。本次耗时最长的就是把它误判成三个独立故障。

## 十五、事故：抽样复跑覆盖了当天的全量数据集

### 发生了什么

21:09，08:30 数据层巡检 Bot 按自己的提示执行了"若失败率 > 5% 或某环节覆盖率 < 80%，
可抽样复跑 `node web\scripts\run_collect.cjs --limit=40`"。

**它老老实实执行了，而这条命令把当天的全量数据集覆盖了**：

| 项 | 覆盖前 | 覆盖后 |
|---|---|---|
| `data/daily/2026-10-21.json` | 619 家 / 4,962KB | **40 家 / 402KB** |
| `out/digest-2026-10-21.json` | 740KB | 263KB（40 家版本） |
| `data/status.json` | 619 家 | 40 家 |

根因很朴素：`run_collect.cjs` 的 `--limit` 只是限制了**采多少家**，但**写盘路径完全一样**。
全量跑和抽样跑都写 `data/daily/<日期>.json`、都写 `status.json`、都生成正式 digest。
"抽样"这个动作在设计上就没有和"全量"隔离。

### 修复

`run_collect.cjs` 现在按 `isSample` 分流：

- 抽样结果写到 `data/samples/<日期>-limit<N>.json`，**不碰**主数据集；
- 抽样运行**不生成**正式摘要（否则会把给 Bot 用的全量摘要换成 40 家版本）；
- 抽样状态另存 `data/status-sample-limit<N>.json`，**不覆盖** `data/status.json`；
- 日志明确打出「抽样复跑结果已隔离保存，未覆盖当日全量数据集」。

### 实测验证

```
抽样前：主数据集 4,963KB | status.json 21:12:06 | digest 740KB
抽样后：主数据集 4,963KB | status.json 21:12:06 | digest 740KB
主数据集未被覆盖: True | status.json 未被改写: True | digest 未被改写: True
样本独立落在：data/samples/2026-10-21-limit40.json (402KB)
主数据集公司数：619
```

同时把 08:30 调度 prompt 里的抽样说明改成"结果写到 `data\samples\...`，不会覆盖全量数据，
**绝不可用它替换主数据**"，并加进硬规则。

### 教训

1. **"采样/试跑"这类动作必须与主产物物理隔离**，不能只靠参数区分。共享写盘路径 = 迟早覆盖。
2. **给 Bot 的指令要假设它会一字不差地执行**。这次不是 Bot 犯错，是我的提示词让它执行了一个有破坏性的命令，
   而我没给这个命令加保护。**凡是指令里出现的写操作，都要先确认它不会破坏既有产物。**
3. 全量数据被覆盖后能恢复，靠的是"采集本身可重跑"（66 秒）——这也说明**采集幂等且可重放**是这套系统该有的属性。

## 十七、卖方观点的三层结构：必须按层引用，不能混用

同一个"卖方观点"在摘要层里存在于**三个不同深度**的字段，混用会直接产出失真结论。

| 层 | 字段 | 本期规模 | 能写什么 |
|---|---|---|---|
| 第 1 层 | `brokerViews[]` | **13 条** | 近 7 天研报的「投资要点」**原文**（thesis + excerpt + 券商 + 日期 + 评级）——**可直接引用原话** |
| 第 2 层 | `companies[].sell_side_view` | **27 家** | 被覆盖公司最新一篇（90 天窗口）的观点原文——可引用；无该字段写"未取到研报正文" |
| 第 3 层 | `companies[].sell_side` | **229 家** | 仅有评级 / EPS·PE 预测 / 标题等**元数据**——**不得当研报原文引用，更不得据标题脑补结论** |

### 顺带修掉一个误导性结构

原来 `sell_side_view` 写成"只要被覆盖就给一个 `{thesis, excerpt}` 对象"，
结果摘要层 178 家里有 **148 家带着 thesis/excerpt 全为 null 的空壳对象**——
看结构像"148 家都有观点原文"，实际只有 25 家真抓到（摘要层 178 家中）。

**空壳对象比缺字段更有误导性**：字段缺失会被读者自然忽略，空壳会被当成"有数据但为空"。
已改为**只在真有原文时才输出该字段**，并加 `digest.sellSideViewStats` 给出三层可核对计数 + 警示语。

## 十八、研报正文抓取：51% → 100%（根因是解析器，不是接口）

### 现象

抓研报「投资要点」正文时，55 篇目标里 **27 篇返回"无正文"**，成功率只有 51%。

### 根因：页面变体没覆盖，不是数据缺失

问题在**不同券商的研报页，小节标题不一样**：

- 28 篇用「**投资要点**」
- 27 篇用「**盈利预测及投资建议**」

**"抓不到"必须先分清是"没有"还是"没解析出来"**——这两者的处置完全不同，

### 修的过程里又踩两个坑（都是"改好了但更糟"）

1. **直接加候选标记 → 质量崩了**：把「投资建议」也加进候选，命中率立刻到 100%，
   但「投资建议」出现在**页脚免责声明之后**（@2271），抽出来是
   *"据此操作，风险自担。东方财富 扫一扫下载APP…"*——**把页脚当券商观点写进简报，比抓不到更糟**。
2. **换更稳的锚点后正则又写错**：研报页里是「萤石网络(**688475**)」**没有 .SH 后缀**，

### 最终解法（55/55 成功、0 噪声）

- **锚点优先级**：**公司行**（`[\u4e00-\u9fa5A-Za-z*]{2,12}\(\d{6}(?:\.(?:SH|SZ))?\)`，正文起点最稳）

- 切到「风险提示 / 免责声明 / 郑重声明 / 数据来源 / 今日最新研究报告」为止；
- **噪声拒绝**：正文出现 `扫一扫下载APP|东方财富|Choice金融终端|风险自担` 等页脚特征 → 判为"没抓到"，宁缺勿滥；
- 正文起点后若紧跟已知小节标题，去掉标题本身。

### 收益

| 层 | 修复前 | 修复后 |
|---|---|---|
| 第 1 层 `brokerViews`（近 7 天研报原文，可直接引用） | 13 条 | **18 条** |
| 第 2 层 `sell_side_view`（被覆盖公司最新一篇原文） | 25 家 | **51 家** |

### 教训

1. **成功率低先看返回体，别先怪接口。**
2. **加候选标记必须同时加噪声拒绝**——召回率上去了而精确率崩了更难发现。

## 十九、看板的局域网模式：读放行、写加锁

看板监听地址已做成开关（`RADAR_HOST`，默认仍 `127.0.0.1`），但**开局域网前必须知道这件事**：

`POST /api/collect` 是**写接口**——它能触发一次全量采集（会打满外部接口、抢连接器配额、
覆盖当日数据集）。服务一旦绑到 `0.0.0.0`，同网段任何人 POST 一下就能触发。

已加保护：**非回环来源必须带对 `RADAR_WRITE_TOKEN`（请求头 `X-Radar-Token`），否则 403**；
本机回环始终放行（本地运维不受影响）。读接口仍是**无鉴权**的——这是"领导直接打开就能看"的代价，
必须由用户拍板接受。

另：服务端缓存绑定在**数据集文件 mtime** 上、且每次请求现取 `latestDate()`，
所以明早 07:30 新数据集落盘后，看板会**自动**切到新一天，不必重启服务。已实测验证。

### 顺带修掉两处服务端小问题

1. `/api/feeds` 路由**重复注册了两遍**（第二份是死代码，第一个分支永远先 return）——已删。
2. `POST /api/collect` 的并发保护还在用旧的"锁文件 mtime"判断，与 `run_collect.cjs`

## 二十、口径硬伤⑦：PE 分位覆盖的算术没闭合（以及一个差点写下的假归因）

### 现象

晨报第一节写「有 PE 分位 **394 / 618** 家（215 家亏损公司 PE 为负，不参与分布）」。
读者拿 394 + 215 = 609 去对 618，**对不上账**。

### 真相：第三类被漏掉了

实际分布（`data/daily/2026-10-21.json` 现场核算）：

```
619 家 = 1 家无 PE（无行情）
       + 403 家正 PE
       + 215 家负 PE（亏损，不参与分布）
403 家正 PE = 394 家有近3年分位 + 9 家近3年分位为空
```

漏掉的就是「**正 PE 但近 3 年分位为空**」这 9 家。

### 成因：一开始我写错了，是核对后改对的

我第一版归因写的是「**上市太短算不出分位**」——**这是错的**。回查 `src/em.js` 的 `pctOf`：

```js
const pctOf = (field, curV, useWindow) => {
  if (!Number.isFinite(curV) || curV <= 0) return null;
  const src = useWindow ? rows.slice(0, windowRows) : rows;
  const hist = src.map((r) => Number(r[field])).filter((v) => Number.isFinite(v) && v > 0);
  if (hist.length < 60) return null;        // ← 窗口内有效正 PE 观测需 ≥ 60
  ...
};
```

真实成因是「**窗口内有效正 PE 观测不足 60 个**」——**亏损年份 PE 为负会被过滤掉**，
所以一家历史 1002 天的公司，若近三年里有大量亏损年份，近 3 年窗口内照样凑不满 60 个观测。

实测 9 家的准确分类：

| 归因 | 家数 | 样例 |
|---|---|---|
| 历史够长、仅近 3 年窗口内观测不足（全历史口径 `pe_percentile_all` 有值） | **1** | 恒烁股份（1002 天，全历史分位 59.7） |
| 真正上市太短（全历史口径也观测不足） | **8** | 芯联集成 836 天 / 昂瑞微 203 天 / 沐曦股份 202 天 / 长鑫科技 57 天 / 频准激光 41 天 / 宇树科技 40 天 / 高凯技术 36 天 / 信诺维 20 天 |

### 修复

- `src/insight.js` 的 `valuationHistoryProfile()` 新增 `peClosure`：闭合式 `formula`、
  两类成因的家数与逐家明细（含历史天数、`pe_percentile_all`、`reason`）。
- digest 暴露该字段；09:10 调度口径要求第一节**照闭合式写**，且**成因不得一律说成"上市太短"**。
- 验收报告新增「估值分位历史长度」取证行。

### 教训

1. **凡是"因为 X 所以 Y"的表述，X 必须验证过才能写进交付物。** 这次我差一步就把
   "上市太短"当成了原因——它对 8/9 成立，对第 9 家就不成立，而那 1 家恰恰是最需要说清楚的一类
   （历史很长，但近三年在亏损，PE 为负被过滤，所以分位算不出）。
   **口径修复本身，也可能引入新的口径错误。**
2. **数字要能闭合。** 凡是把几个数并列展示，读者会自己做加减——对不上的地方就会变成
   "这数据有问题"的质疑。宁可写出完整闭合式，也不要留一个看似能自洽的残缺分母。
3. **"没取到"往往不止一种原因。** `null` 是结果，成因在代码里；写交付物前要回到代码确认门槛在哪。

## 二十二、飞书会把成对的 `~` 当删除线：加两道防线

### 现象

飞书的 markdown→HTML 转换把**成对的 ASCII `~`** 当作 GitHub 风格的删除线标记，生成 `<del>`。
结果是**原文成段内容在飞书端显示为划掉的删除线**，而 lark-cli 全程报成功、
"✓ 落点校验通过"照常打印，**没有任何错误提示**。

本项目的实测：某版晨报正文 40 处 `~` → 飞书端 8 段被包成 `<del>`，
其中「同比增加68%~75%；扣非归母净利润18.65亿元~19.48亿元」整段被划掉。
本地正文看起来完全正常，**只有回读飞书产物才能发现**。

### 为什么这次要专门加防护

当前这一版简报恰好 0 个 `~`（主编重写时自然用了 en dash `–`，48 处），
项目档案里有 15 个 `~` 但**各自单独成块、没有配对**，所以飞书端 `<del>` 恰好也是 0。

**这是运气，不是设计。** 下一次主编写出一个「10.00~12.00 元」或「68%~75%」，
只要同一段里出现两个 `~`，同一批内容就会被静默划掉。

### 两道防线（已落地）

新增 `scripts/md_guard.js`：

1. **发稿前净化**（`sanitizeTildes`）：把正文里作为区间连接符的 ASCII `~` 换成 en dash `–`
   （语义不变，长度相近，视觉一致）。
   **代码块与行内代码一律不动**——项目档案里的 `~/.minimax/bin/mcode-tools-cn.cmd`
   这类路径不能被改。实测：15 个 `~` → 替换 12 个（正文），保留 3 个（1 个行内代码 + 2 个围栏代码块）。
2. **发稿后回读**（`checkStrike`）：`docs +fetch` 拉回产物，`<del>` 数量必须为 0，
   否则**判定发布失败并 exit 2**，并打印被划掉的原文片段。

两个发布脚本都已接入：
- `scripts/publish_brief.cjs`（每日简报）
- `scripts/publish_feishu.cjs`（项目档案）

自测 `.tmp/test_guard.cjs` 验证：正文替换、行内代码保护、围栏保护、`<del>` 计数与样例提取。

### 教训

**凡是"转换器把某个字符当标记"的平台（飞书 `~`→删除线、Markdown 列表前缀变 `<li>`、
全角 `｜` 保留而半角 `|` 被吃），CLI 不会告诉你，只有回读产物本身能验证。**

因此发布后固定检查三件事：
1. 产物里**不该出现**的标记（`<del>`、残留 Markdown 记号）；
2. 链接**去重后**数量与本地一致（比总数可靠）；
3. 逐行落地率——比对前必须先归一化（剥列表前缀 `- ` / `1. `、把全角 `｜` 视同半角 `|`、
   解 HTML 实体），否则会把格式差异误判成内容丢失。

- 行业筛选跨天漏公司（筛"半导体"会漏掉标着"集成电路"的公司）

### 2026-10-22 16:45 无人值守链路实测：计划任务在电池上根本不启动

**现象**：10:30 保底发布任务 `MavisKcbRadarFallback` 注册了、启用了，但
`Last Run Time = 1999/11/30`、`Last Result = 267011`（任务尚未运行）——
**它从来没有真正执行过**。昨天那份 10-22 简报是我手动发的，不是任务发的。

手动 `schtasks /run` 后，任务状态一直是 **Queued**，进程列表里连 node 都没有。

**根因**（`schtasks /query /xml` 查出来的）：三个任务都带
`<DisallowStartIfOnBatteries>true</DisallowStartIfOnBatteries>` +
`<StopIfGoingOnBatteries>true</StopIfGoingOnBatteries>`，
而当时机器 `Win32_Battery.BatteryStatus = 1`（正在用电池，61% 电量）→ **电池供电时任务不启动**。

**这意味着**：笔记本拔电时，07:30 采集、08:05 看板、10:30 保底**全部静默不跑**，
任务状态只显示 Ready/Queued，**没有任何报错、没有任何告警** —— 表现就是"简报没更新"。

**修复**（三个任务统一）：

```
DisallowStartIfOnBatteries = false   # 允许电池供电时启动（三个任务都是 2 分钟级短任务）
StopIfGoingOnBatteries     = false   # 切到电池也不中途杀
StartWhenAvailable         = true    # 到点时机器关着/睡眠，醒来后补跑
```

**修复后实测**：`schtasks /run MavisKcbRadarFallback` → 状态 Running，
进程链 `fallback_publish.cjs → publish_brief.cjs → lark-cli` 真实跑起来，
16:46 发布完成，`Last Result = 0`，飞书 10-22 简报已带「本期为确定性基线版」注记重发（77,265 字符）。

**⟹ 判据：判断"无人值守链路是否真的在跑"，不能看任务是否注册/启用，
要同时看 ① Last Run Time 不是 1999 ② Last Result = 0 ③ 任务 XML 里没有
"电池不启动"这类隐性前置条件。**

## 三十四、看板静默卡死：端口在听，但 HTTP 全死（2026-10-27 13:23）

### 34.1 事故形态

10-27 下午打开看板无响应。排查结论：

| 观测 | 结果 |
|---|---|
| 端口 7788 | **仍在 Listen**（TCP 握手能成功）|
| HTTP 请求 | 全部超时（回环与内网地址都一样）|
| CPU 增量 | 10 秒内 **0.00s**（不是忙等，是在"等"）|
| 内存 | 24.8MB（进程几乎空的）|
| 10 个 socket | 停在 `CloseWait` |
| `data/access.log` | **停止写入** |
| 当天计划任务 | `LastResult=0` —— 报的是**成功** |

**最危险的不是它死了，是它"看起来是好的"**：端口在听、任务报成功，
而看板对所有人都是死的，而且从 13:23 到 14:5x 无人察觉。

### 34.2 为什么会报"成功"

`scripts/start_web.cmd` 原来只用 `netstat -ano | findstr LISTENING` 判断服务是否起来。
**卡死的服务同样满足这个条件** —— 监听套接字在，端口就"在听"。
另外新实例在端口被占时会 `process.exit(0)`（EADDRINUSE 分支），
于是「旧进程卡死 + 新进程秒退」= 计划任务看到退出码 0 = "一切正常"。

**⟹ 判据：判断服务是否活着，必须发一个真实请求。
`netstat` 只能证明内核在监听，不能证明应用还在应答。**

### 34.3 为什么会卡死：看板自己在打自己

看板首屏会同时打出**几十个**区间请求（不同日期组合 × 不同行业）。而：

- `store.loadDataset()` **完全没有缓存** —— 每次调用都把 5MB 的 JSON 重新读盘 + 重新解析；
- `aggregateRange()` 对窗口内**每一天**都调一次 `loadDataset()`。

于是 30 个请求 ≈ 120 次全量数据集解析。实测（修复前）：

| 指标 | 修复前 | 修复后（第 1 轮） | 修复后（缓存命中）|
|---|---|---|---|
| 30 个并发请求总耗时 | **8817ms** | 669ms | **135ms** |
| >3s 的慢请求 | **20 个** | 0 | 0 |
| 期间探活 | **超时 8 秒** | 16ms | 3ms |
| CPU 消耗 | +9.0s | +0.83s | +0.16s |
| 进程内存 | 84 → 248MB | 65 → 141MB | 141 → 144MB |

**⟹ 判据：一个只读接口被并发打几十次时，
先问"每次调用重做了多少重复功"，而不是先加机器。
`全量文件 × 无缓存 × 并发` = 自己把自己打死。**

### 34.4 三道防线

**① 缓存（治本）**
- `src/store.js`：`loadDataset` 加**进程级缓存**，按**文件 mtime + size** 判定失效
  （采集写新文件 → mtime 变 → 缓存自动作废），LRU 上限 5 份；
- `src/range.js`：`aggregateRange` 加**记忆化**（key = from|to|行业集合，TTL 60 秒），
  数据集变更时由 `server.getBrief` 调 `clearRangeCache()` 作废。

**② 启动要真探活（治"假成功"）**
`scripts/start_web.cmd` 改为：
1. 启动前**杀掉占用端口的僵尸进程**（否则新实例 EADDRINUSE 秒退）；
2. 启动后跑 `node scripts\healthcheck.cjs --wait 40` —— **发真实 HTTP 请求**，
   拿不到 200 就 `exit 1`，让计划任务如实报失败。

**③ 看门狗（治"死了没人知道"）**
`scripts/healthcheck.cjs`：
- `--probe`：探活并打印（退出码 0=健康 / 1=不健康）
- `--wait N`：等到健康为止（给启动脚本用）
- `--repair`：不健康就**杀掉卡死的监听进程并重启服务**，日志落 `data/health.log`

新增计划任务 **`MavisKcbRadarHealth`**，每 15 分钟跑一次 `--repair`。

### 34.5 自愈演练（端到端实测）

用"只接受连接、永不响应"的假监听器**精确复现**卡死形态（探活 5s 超时），然后：

```
[health] UNHEALTHY (timeout) — repairing
[health] killing stuck listener PID 41316
[health] started new server PID 50548
[health] RECOVERED (200, 1024B, 15ms)      用时 14.7s
```

断言 5/5 通过：卡死已复现 / 退出码 0 / 僵尸被杀 / 服务重起 / 探活恢复。

### 34.6 cmd 的两个坑（这次都踩了）

1. **FOR 块里未转义的 `)` 会提前结束代码块** ——
   `echo ... (PID %%P)` 里的 `)` 让 cmd 把 `taskkill` 那行解析成了别的东西，
   表现为"日志打了 kill、进程却没死"。**判据：cmd 脚本里 FOR/DO 块内不要出现裸括号。**
2. **`.cmd` 必须纯 ASCII**（老规矩，OEM 码页 936 会把 UTF-8 注释打散成 9009）。

### 34.7 顺带修掉的两个"署名不实"

- `board.js` 的 `ifindCovered` 曾被改成「iFinD 补充口径覆盖家数」，
  额度耗尽时 Mini App 会显示「覆盖 **0** 家财务/评级」——
  与事实相反（财务实际覆盖 618/619）。**已改回原语义，新语义另起 `ifindSupplement`。**
- `board.js` 的 `financialCovered` 一度恒为 0 —— 它在 `mapCompany` 之后的看板视图对象里
  取 `c.revenue`，而那个对象根本没有这个字段（在 `revYoY`）。**必须从 `dataset.companies` 取。**

## 三十五、历史回补：把 10-24/25/26 补回来（2026-10-27）

### 35.1 缺口成因

10-27 补跑采集时发现 **10-24 / 10-25 / 10-26 三天没有数据集**（10-26 是周一交易日）。
TaskScheduler 运行日志证实：这三天**一次都没触发**，10-27 09:31:08 三个任务**同时补跑** ——
机器那几天不可用（关机/休眠），`StartWhenAvailable` 在恢复可用时一次性补上。

### 35.2 为什么不能直接用「再采一次」补

行情快照（东财 push2 clist）只给**此刻**的行情。事后补采拿到的会是 10-27 的价格，
却标成 10-24 / 10-26 —— **那是编造，不是回补**。所以必须换数据源。

### 35.3 回补用的两个权威源（都是按日的真实数据）

| 源 | 提供的字段 | 角色 |
|---|---|---|
| `RPT_VALUEANALYSIS_DET`（东财 datacenter，`columns=ALL`） | **PE_TTM / PB_MRQ / PS_TTM / PCF / PEG** / **总市值 / 流通市值 / 总股本 / 流通股本** / **收盘价** / **涨跌幅** | **主口径** |
| `push2his` 日 K 线（`klt=101&fqt=0`） | 日期 / 开 / 收 / 高 / 低 / 成交量 / 成交额 / 振幅% / 涨跌幅% / 涨跌额 / **换手率%** | **可选增强**（只补 K 线独有的成交明细） |

两者都是**逐日**的，回补出来的每一天都是那一天的真实口径，不需要任何推算。

**为什么是「估值序列为主、K 线为辅」**（2026-10-27 实测踩出来的）：
第一版把日 K 线当主口径，跑完发现 **10-26 只有 335/619 家取到了 K 线**，
查下去是 **push2his 在高频请求下整片 ECONNRESET** ——
回补 15 分钟打了约 3,700 次请求后，连打 12 只全部被拒；
而**同一时段 datacenter 的估值序列 618/619 家全部正常**。
更要命的是，我的代码把 `getJson` 的异常吞成了空数组，于是那 284 家**静默地丢了涨跌幅和换手率**。

改法两条：
1. **主口径换成估值序列** —— 它的 `CLOSE_PRICE` 与 `CHANGE_RATE` 就是当天的收盘价与涨跌幅，
   实测与 K 线**逐字一致**（亚虹医药 10-26：K 线 -1.50 / 估值序列 -1.496259…）；
2. **K 线降级为增强 + 熔断** —— 连续失败 20 次就整轮不再请求日 K（不加重封禁），
   换手率/成交量/成交额/振幅拿不到就留空，**并在降级项里如实写明**。

**⟹ 判据：选主口径要看"哪个源更稳"，不是"哪个源字段更多"。
高频接口当主口径 = 把它当成必然成功的；而静默吞异常会把"没取到"伪装成"没有数据"。**

### 35.4 三个必须处理的口径问题（都是实测踩出来的）

**① 要闻池必须裁到目标日期**
要闻是"按公司名搜当前池子"，返回的是**此刻可见**的条目。
不裁剪的话，「10-24 的数据集」里会装着 10-27 的新闻 —— 简报的锚定日变成 10-27，整份简报答非所问
（`insight.js` 的 `latestDate` 取的是池内最大日期）。
→ 回补时按 `n.date <= 目标日` 裁剪，并把每家的取数条数从 12 提到 30（活跃公司几天就能刷掉 12 条）。

**② 要闻缓存必须按条数失效，且回补要用独立缓存文件**
- 只看 TTL 不看条数 → 回补拿到 12 条的旧缓存，裁剪后几乎什么都不剩；
- 共用缓存 → 明早的实时采集会拿到 30 条的池子，把线上「要闻 N 条」的规模改掉。
→ 缓存命中条件加「条数够」，回补走 `data/news-cache-backfill.json`。

**③ 非交易日（周末/节假日）**
K 线里没有该日 → 收盘价沿用**最近交易日**并标注；**当日涨跌幅按 0 计**（当日无交易，日涨跌按定义为 0）；
换手率/成交量/成交额**留空**（当日确实没有成交）。
这样"休市日"在看板里表现为「涨 0 / 跌 0 / 平 N」，语义正确，而不是拿上一交易日的涨跌幅冒充。

### 35.5 实测（独立路径交叉验证）

直接打 `push2his` 原始行 vs 回补产出：

| 公司 | 原始行（2026-10-26） | 回补产出 | 一致 |
|---|---|---|---|
| 睿创微纳 | 收盘 147.76 / 涨跌幅 -3.52 / 换手 1.86 | 收盘 147.76 / -3.52 / 1.86 | ✅ |
| 天准科技 | 收盘 67.61 / 涨跌幅 -2.64 / 换手 4.96 | 收盘 67.61 / -2.64 / 4.96 | ✅ |

休市日（10-24）：锚定 2026-10-23、涨跌幅 0、成交数据留空 ✅。

### 35.6 回补日与实时采集日的两个不可比口径（必须写进正文）

1. **要闻总数不可直接比**：回补每家取 30 条（线上 12 条），因为检索返回的是"此刻可见"的池子，
   只取 12 条盖不到目标日期。10-24 的要闻 11,478 条 vs 10-27 的 4,802 条，
   **不是那天新闻更多，是取数窗口更大**。→ 简报里新增「本期为历史回补（口径差异须知）」段落写清楚。
2. **要闻池按目标日期裁剪**：不裁剪的话「10-24 的数据集」里会装着 10-27 的新闻，
   简报锚定日会变成 10-27，整份简报答非所问（`latestDate` 取的是池内最大日期）。

### 35.6 实现要点

- `src/history.js`（新）：`fetchDailyKline()` + `buildHistoryQuotes()`（逐家 2 个请求，并发 5）
- `src/em.js`：`fetchValuationHistory(code, {asOf, full})`
  - `asOf`：**分位只能用该日及之前的历史算**（不能用未来数据）
  - `full`：多要总市值/股本/PCF/PEG
- `src/collector.js`：`collectAll({ backfill: true })` 分支
- `scripts/backfill.cjs`（新）：回补入口，按日期升序跑（跨日差分要以上一日为基准），
  **研报正文从参考数据集按研报 id 复用**（省掉每天 231 次重复抓取），
  状态另存 `data/status-backfill-<日期>.json`，**不覆盖** `data/status.json`（那是实时采集的状态）
- 数据集里写 `backfill: {mode, asOf, quoteDate, tradingDay, covered, exact, note}` —— 回补数据必须自带标记，
  否则看板/简报会把回补当实时数据读

### 35.7 踩到的两个 bug（都是"取反了"）

1. **K 线取错那根**：klines 按日期**升序**，写成"遇到第一个 ≤ date 就 break"会取到**最早**的一根 ——
   实测把 10-26 错取成 10-08。正确做法是一路覆盖、取最后一个。
2. **分位窗口取反**：`rows` 按日期**倒序**，`asOf` 及更早的行是 `rows.slice(idx)`，
   写成 `rows.slice(0, idx+1)` 会把 **asOf 之后**的行也算进分位窗口 → 历史天数只剩 2 天、分位全空。

**⟹ 判据：同一份数据"正序还是倒序"必须在两个地方同时确认 ——
取"最近一条"和取"区间"的方向常常相反，写完要用独立路径核对一根。**

> 本节记的是**第三十六节上线后暴露的三个坑**。它们的共同特征是：

### 37.1 引用格式：提示词写软了，模型就不守规矩

第三十六节首轮评估 14/15，唯一不合格的是**行业类回答没有按格式用 `[E编号]` 引用**
（内容仍基于材料，只是没编号）。根因不在模型，在提示词：

- 原 system prompt 把引用规则写在第 4 条，夹在"不做投资建议""结论先行"中间；
- user prompt 的材料段标题只写了「（引用时请用 [E编号]）」——**"请"字是软的**。

改法（三处同时收紧）：

1. system prompt 把引用规则**提到最前**，并加一条硬约束：
   **「没编号的依据不要写进答案 —— 没有编号，读者就没法回查；这条比"写得好看"重要。」**
2. user prompt 的材料段标题改成硬措辞，并补三条：
   「凡是来自下面材料的结论，句末必须标出来源编号」「**没有编号的依据不要写进答案**」
   「只引用下面出现的编号，不要自己编 [E7] 这种不存在的编号」。
3. 结尾的提问行再加一遍要求（结论先行 + 标编号 + 没覆盖就明说）。

改完：点名公司题出现 `[E12][E9][E10]`，行业类题也带编号 → 评估从 14/15 到 **20/20**。

### 37.2 推理模型把 max_tokens 烧光，正文被砍成半截

**现象**：日志里 `completion_tokens` 反复**正好等于 2000** —— 那不是"回答短"，是**被砍了**。

**根因**：`deepseek-flash` 是**推理模型**，先烧 `reasoning_tokens` 再写正文。
而 `RADAR_LLM_MAX_TOKENS=2000` 是**整个输出**的预算（含推理）。
于是推理吃掉大部分 → 正文被 `max_tokens` 截断 → `finish_reason=length`。

**致命的地方**：半截答案**看起来是完整的**。它照样有开头、有结构，
只是后面的结论和引用编号没了 —— 比报错危险得多。

**探测：哪种开关真的有效**（同一份材料，六种参数组合实测）：

| 参数写法 | 推理 token | 结论 |
|---|---|---|
| 默认 | 184~266 | 推理开着 |
| `max_tokens=16000` | 215 | 接口接受，但**推理照样烧**，正文仍可能被砍 |
| `reasoning_effort: 'low'` | 241 | **被接口忽略**（推理没降） |
| `enable_thinking: false` | 266 | **被接口忽略** |
| **`thinking: {type: 'disabled'}`** | **0** | ✅ **只有这个真的生效** |

**最终处置（三层）**：

1. **默认关推理**（`RADAR_LLM_THINKING=off` → 请求带 `thinking:{type:'disabled'}`）。
   理由：材料本就是结构化好的（编号证据 + 当日上下文），让模型再推一遍收益很小；
   而推理一长，正文就被砍。**要开随时改 env，改完即生效，不用重启。**
2. **截断显式拦截**：`finish_reason==='length'` 直接抛 `LLM_TRUNCATED`，
   **绝不把半截答案当成正常结果交出去**。
3. **截断自动重试**：上限翻倍 + 明确要求"直接给结论、控制在 400 字以内"，自动重试一次。

同时把上限 2000 → **8000**、超时 90s → **180s**（推理模型出文慢，90s 会假报超时），
并在 system prompt 里加了**长度预算**：「正文控制在 400 字以内，最多列 6 条依据」。

**实测收益**：响应 **12.5 秒 → 2.3~3.7 秒**；质量评估 **14/15 → 20/20**；
Mini App 代理 5/5。关推理同时解决了"慢"和"被截断"两个问题。

### 37.3 改了 radar.env 却没生效 —— 优先级反了

**现象**：把 `RADAR_LLM_MAX_TOKENS` 从 2000 改成 8000，`/api/status` 里**还是 2000**。

**根因**：`src/env.js` 原本是「**进程环境变量 > 文件**」。
但启动脚本（`start_web.cmd` 与 `healthcheck --repair`）**会把 radar.env 灌进进程环境** ——
于是进程环境成了**启动时的一份快照**，之后改文件永远不生效。
`env.js` 注释里写的"延迟读、改完 key 不用重启"这句话，**对已经在进程环境里的键是假的**。

**改法**：优先级翻成「**文件 > 进程环境**」，进程环境只在文件里没写该项时兜底。
改完：改 `radar.env` → `/api/status` 立刻变新值，**不用重启**。
（`env.js` 的**代码**改动仍需重启 —— 运行时重读的是文件内容，不是代码。）

### 37.4 服务在问答期间不响应，而且过程无痕

**现象**：评估跑到第 2 题，服务就不应答了；健康任务探活超时 → 杀掉 → 重启 → 恢复。
访问日志里第 2~5 题**一条记录都没有**，像是请求从没到达。

**排查链路**（这次是可复现的，不是猜）：

1. 健康日志给出直接线索：`[08:54:59] UNHEALTHY (timeout) — repairing`。
2. 加了**分阶段计时**后一次看清：
   `loadDataset=2ms getBrief=214ms retrieve=33ms buildPrompt=5ms llm=11308ms`
   —— **本地各阶段都不慢，11 秒全在模型调用**（那次调用本身被截断）。
3. 单独测各阶段（绕开 HTTP）：warm 900ms、brief 330ms、retrieve 31~106ms、prompt 3ms。
   **问答路径本身不是瓶颈。**
4. 真凶是**启动预热**：`setImmediate(() => { warmUp(); })` 注释写着"后台预热，不阻塞启动"，
   但 `warmUp` 是 `async` **函数体却完全同步**（里面一个 await 都没有）——
   **`async` 不等于异步**，`setImmediate` 只是把它挪到下一个 tick，并没有让它并发。
   预热一次性 JSON.parse 7 份 8MB 数据集 → **事件循环被堵住** → 期间所有请求排队没人应答 →
   探活超时 → 看门狗只能杀进程。

**四条防线（已落地）**：

| 防线 | 做法 | 挡住什么 |
|---|---|---|
| 预热让出 | `warmUp` 每份数据集之间 `await setImmediate` | 不再堵事件循环（实测预热 660ms 且期间仍可应答） |
| 事件循环看门狗 | 每秒测 lag，>2000ms 落盘报警；`/api/status` 暴露 `loopLag` | 卡死**有证据**，不再只剩"端口还在听"的假象 |
| 崩溃留痕 | `uncaughtException`/`unhandledRejection` 落盘后退出；`start_web.cmd` 把 stdout 重定向到 `data/server.log` | 服务一崩就有现场，不用靠猜 |
| 分阶段计时 | `/api/ask` 记录每段耗时并写进台账 | 下次再慢，能一眼看出卡在哪一步 |

> **这一节的通用教训**：**"async 函数"不等于"不阻塞"**，
> **"端口在监听"不等于"服务活着"**（第三十四节已踩过一次，这次是同一类错误的第二个变体）。
> 判断服务健康必须发**真实请求**，而且要能看到**请求被处理的过程**。

### 37.6 界面端到端实测时发现的真 bug：问答页被筛选栏整个盖住

**症状**：接口全绿（评估 20/20、Mini App 代理 5/5），但在**浏览器里根本没法提问** ——
点「提问」没反应、页面一直是「还没有提问」。

**排查过程**（每一步都有证据，不是猜）：

1. 服务端访问日志里**没有** `POST /api/ask` → 请求根本没发出去，不是后端问题。
2. 控制台 0 报错、页面没有异常 → 不是 JS 报错。
3. 截图一看就明白了：**`.filterbar`（行业标签 + 日期 + 口径说明 + 数据来源行）实测高约 420px，
   而 720px 的视口只剩一半；而它是 `position: sticky`**。
   于是页面一滚动，它就盖住正文 —— 而问答页的输入框和「提问」按钮**正好是面板最上面的元素**：
   - 往下滚 → 输入框被顶到筛选栏下面（更点不到）；
   - 不滚 → 输入框在筛选栏下沿，点下去落点其实打在筛选栏上。
   **看得见却点不到**——按钮点了没反应，就是这个原因。
4. 顺带发现：**tab 行也是 sticky 的（top:63px），而筛选栏更高、z-index 更大**，
   所以一滚动 tab 行就被盖住（切换 tab 只能靠"点了刚好没被盖住"的运气）。

**修法**（三行改动）：

- `public/style.css`：`body.tab-ask .filterbar { position: static; }`
  —— 问答页不需要行业/日期筛选（提问自带语义检索），这一页让筛选栏随页面滚走。
- `public/app.js`：`activateTab()` 里 `document.body.classList.toggle('tab-ask', state.tab === 'ask')`。
- 切到问答页时 `window.scrollTo({top:0})`，保证输入框在视口内。

**修完的实测**（浏览器实拍）：

| 路径 | 结果 |
|---|---|
| Ctrl+Enter 提交 | ✅ POST /api/ask → 200，3.3 秒，页面渲染结论 + 带编号依据 + 「本期数据没有覆盖」 |
| 点「提问」按钮 | ✅ POST /api/ask → 200，3.3 秒，同上 |
| 示例问题 chip | ✅ 可点（之前因输入框被盖，点击同样落空） |
| Mini App 问答区块 | ✅ 浏览器实测渲染完整（答案 + 依据折叠 + 提示词折叠） |

**⟹ 通用教训**：**接口全绿 ≠ 功能可用。**
这一版的三层验证（质量评估 20/20、代理 5/5、验收 12 项）**全绿**，
但没有一层会"在浏览器里点一下按钮"——所以一个**纯 CSS 遮挡**bug 从头到尾没被任何自动化发现。

### 38.2 顺手修掉：`start_web.cmd` 的日志路径拼错 + stdout 根本没被重定向

**两个叠在一起的 bug**：

1. **路径少一个分隔符**：`WEB_DIR` 结尾是 `..`，所以 `"%WEB_DIR%data\server.log"`
   展开成 `...\web\scripts\..data\server.log` —— 建出来一个**名字就叫 `..data` 的野目录**，
   而不是 `web\data\server.log`。
2. **更根本的**：`start "" /min node ... >> file` 里，重定向句柄属于 **`start` 自己**，
   **子进程并不继承** —— 实测那个文件是 **0 字节**，服务日志一条都没进去。

**修法**：**落盘这件事交给进程自己做**，不再依赖"谁拉起的我"。
`src/server.js` 里加 `teeConsole()`：把 `process.stdout/stderr` 的写入同步复制到
`data/server.log`（同步写，进程被杀前写进去的日志不会丢）。
启动脚本里那段无效重定向直接删掉。

**实测**：重启后 `data/server.log` 里能直接看到启动横幅、预热行、请求行 —— 不依赖任何启动器重定向。

> **⟹ 通用教训**：**"重定向日志"这种做法要看清楚句柄归谁**。
> `start` / `nohup` / `spawn` 各自的语义不同，**猜不如让进程自己写文件**。

## 四十、看板联网：改用 DeepSeek 自己的联网能力（2026-10-28 11:20）

> **实测三轮**，结论和预期不一样，记在这里。

### 40.1 实测：DeepSeek 网关"只决策、不执行"

| 探测 | 结果 |
|---|---|
| `GET /v1/models` | 只有 `deepseek-flash` / `deepseek-v4-pro`，**没有独立的 search 模型** |
| `tools:[{type:'web_search'}]` | **HTTP 422**：`unknown variant 'web_search', expected 'function'` |
| `enable_search: true` | 无效（模型只在推理里空想"需要联网"，正文为空） |
| `search_options:{enable:true}` | 无效（同上） |
| `search_engine:{name:'bing'}` | **危险**：模型自己说"我无法实时联网核验"，然后**编了一堆网址** |
| **`web_search: true` + function 形式的 web_search 工具** | ✅ **返回标准 `tool_calls`**（还能自动把一个复杂问题拆成 2~3 个查询） |
| `POST /search`、`/v1/search` 等 | 全部 404（网关没有搜索端点） |

**结论**：DeepSeek 网关**支持"模型决定搜什么"**（`web_search:true` + function 工具 → `tool_calls`），
但**网关自己不执行搜索**，把查询甩回客户端。
> **⟹ 教训**：给模型"联网"能力 ≠ 模型能联网。
> 而且实测里最危险的不是"搜不到"，是 **`search_engine` 那个变体——模型会一本正经地编造来源网址**。
> 所以联网层必须**由我们自己取回真实内容**再喂回模型，绝不能让模型"凭印象"给链接。

### 41.5 通用教训

**⟹ 写"项目背景"时必须分清三件事**：

**⟹ 凡是"系统覆盖 X，但用户更关心 Y"的项目，Y 必须写成显式的条件分支，不能并进范围描述里。**

### 43.7 插曲：免费搜索后端被按频率封了（连带修了两处）

部署准备做完后跑验收，发现**联网证据是 0 条**。查下来不是代码错，是**DuckDuckGo 把我们封了**：

```
DuckDuckGo html 端点 → 连试 3 次全部 ECONNRESET
```

起因是这两轮为了测各种写法，短时间内打了几十次 DDG。**免费后端会按频率封 IP** ——
表现是"联网突然失效"，而且**没有任何业务层报错**。

**⟹ 这暴露了单后端 = 单点故障。** 于是加了三层：

| 层 | 做法 |
|---|---|
| **降级链** | `provider=auto` 时按 `key 后端(tavily/brave/serpapi) → duckduckgo → so360(360搜索)` 依次尝试，前一个失败自动落下一个 |
| **进程内缓存** | 同一 query **10 分钟**内不重复打后端（缓存 TTL + 容量 50） |
| **请求节流** | 同一后端两次请求最小间隔 **900ms** |

**新后端：360 搜索**（免 key）。它的结构与 DDG 不同：
`<div class="res-list"><h3 class="res-title"><a href="...so.com/link?m=…" **data-mdurl="<真实网址>"**>标题</a></h3><p class="res-desc">…</p></div>`
—— **真实网址在 `data-mdurl` 属性里**（href 是 360 自己的跳转链）。
实测能拿到正确结果（雪球/第一财经/澎湃新闻）。

**其它候选后端的实测结论**（省得以后再试）：

| 后端 | 结果 |
|---|---|
| Bing RSS（`format=rss`） | 能通，但**结果完全跑题**（中文 query 被理解成"西尔布利山"旅游攻略）→ 不可用 |
| 百度 | 能通但结果链接是 JS 跳转，解析不出 → 不可用 |
| 搜狗 | 能通，但链接是 `/link?url=…` 二次跳转 → 解析麻烦，暂不接 |
| **360** | ✅ 可用（data-mdurl） |

**⟹ 所以最终建议还是给一个搜索 API key**（Tavily/Brave 都行，免费额度足够）：
免 key 链路现在能跑，但**它随时可能再被封**；配了 key 就走稳定通道，没有 key 才降级到免 key 的。

### 43.8 连带修掉的两个自己的错

1. **验收的"key 泄露"扫描误报**：`/RADAR_LLM_API_KEY\s*=\s*\S/` 会把
   `RADAR_LLM_API_KEY='',` 这种**模板占位**也判成泄露 → 改成要求 **20 位以上的真实值**。
2. **我写补丁脚本时把 env 文件改坏了**：追加配置忘了先补换行，

   `RADAR_LLM_THINKING=offRADAR_SEARCH_PROVIDER=auto`；

> **⟹ 教训**：**改配置文件的脚本要"只改目标键、其余原样保留"**，不要用正则去"整理"整行 ——
