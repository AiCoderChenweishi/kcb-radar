## 14. 问答可靠性回归（2026-10-27 推理模型截断与静默卡死的复盘）

> 这一节守的是**上一轮踩的三个坑**，都是"看起来正常、实际不可靠"的那一类：
> ① 推理模型把 max_tokens 预算烧光 → 正文被砍成半截（**半截答案比没有答案危险**）；
> ② 改了 radar.env 却不生效（进程环境是启动时的快照，把文件盖住了）；
> ③ 服务在问答请求期间不响应，探活超时只能靠杀进程自愈，**过程无痕**。

| 回归项 | 实测 | 判定 |
|---|---|---|
| 配置改动即时生效（env 优先级：文件 > 进程环境） | radar.env max_tokens=8000 / thinking=off / timeout=180000ms；服务实读 8000 / off / 180000ms | ✅ |
| 截断被显式拦截 | llm.js 检测 finish_reason=length 并抛 LLM_TRUNCATED（不交付半截答案） | ✅ |
| 截断自动重试 | 截断后上限翻倍 + 明确要求写短，自动重试一次 | ✅ |
| 推理可关闭 | 请求带 thinking:{type:'disabled'}（实测只有这个开关生效） | ✅ |
| 提示词有长度预算 | system prompt 含「长度预算：正文控制在 400 字以内」 | ✅ |
| 引用规则写死 | user prompt 含「没有编号的依据不要写进答案」硬措辞 | ✅ |
| 事件循环有看门狗 | server.js 有 lag 看门狗，/api/status 暴露 loopLag | ✅ |
| 预热不阻塞事件循环 | warmUp 每份数据集之间让出（setImmediate） | ✅ |
| 崩溃留痕 | uncaughtException/unhandledRejection 落盘后退出；start_web.cmd 把 stdout 重定向到 data/server.log | ✅ |
| 问答分阶段计时 | /api/ask 记录 loadDataset/getBrief/retrieve/buildPrompt/llm 各段耗时 | ✅ |
| 问答页不被筛选栏遮挡 | 问答页把 .filterbar 改成非 sticky（否则 420px 高的 sticky 筛选栏会把输入框整个盖住，点「提问」点不到） | ✅ |
| 问答端到端可用 | POST /api/ask → 200，答案 802 字，含 [E编号]：是 | ✅ |

> **为什么关掉推理**：deepseek-flash 先烧 reasoning_tokens 再写正文。材料本就是结构化好的
> （编号证据 + 当日上下文），让模型再推一遍收益很小；而推理一长，正文就被 max_tokens 砍断。
> 实测同一份材料：开推理 completion 242~330（推理占 184~266）；关推理后推理 0 字，
> 响应时间从 12.5 秒降到 2.3~3.7 秒，且不再截断。
> 需要开推理时把 radar.env 的 RADAR_LLM_THINKING 改成 on（无需重启，改完即刻生效）。
